## 需求理解

一句话：希望把 BambooHR 的「List Time Off Requests」接口封装成一个可被 assistant/聊天调用的工具（`bamboohr_list_time_off_requests`），让 Daily/Weekly Attendance SOP 能用真实的 BambooHR 请假数据填充 Leave Status 小节，而不是靠人工或间接方式拼凑。

复述：
- 要解决谁的问题：Daily/Weekly Attendance SOP 的执行者（leadership / HR attendance reporting）。
- 要解决什么问题：目前 assistant 没有任何工具能读到 BambooHR 的请假申请数据，Leave Status 小节只能人工填或用间接来源拼凑。
- 成功是什么样：assistant 能调用一个新工具，传入日期范围（单日或整周）即可拿到结构化的请假记录（员工姓名、员工 ID、假别、起止日期、状态、时长），用于生成 Leave Status 小节。
- 工单原文的「Existing Capability Check」称「已在 wiki 确认 BambooHR 连接器存在且提供运行时工具、覆盖员工与请假数据，但没有确认存在等价于 `bamboohr_list_time_off_requests` 的现成工具」——这条本身与本次代码级核实一致（见下「现状」），因此按新增能力处理，不是重复造轮子。

## 产品设计

### 目标 / 非目标

**目标**：新增一个可被 assistant/聊天调用的只读工具 `bamboohr_list_time_off_requests`，输入必填 `start`/`end` 日期，可选按 `status`/`employeeId`/请假类型过滤，返回结构化 JSON（至少含员工姓名、员工 ID、假别、起止日期、状态、时长/数量），供 Daily/Weekly Attendance SOP 生成 Leave Status 小节使用。

**非目标**：
- 不做「assistant 自动生成完整 Leave Status 文案」——这是 SOP/prompt 层的事，不在本 MCP 工具范围内。
- 不新增「按名称查请假类型 ID」的辅助工具（如 `bamboohr_list_time_off_types`）——工单只要求这一个工具；类型 ID 的可用性问题记入 Open Questions，不阻塞本单。
- 不改动 `mcp-service-gateway` / `mspbots-agent-mcp`——两者都是透传网关，已用代码核实不需要改（见「现状」）。
- 不做 `amount`/`duration` 字段的单位归一化——原样透传上游返回的结构。

### 验收标准 AC1..ACn

- **AC1**：Given 已配置有效的 BambooHR domain/api-key 凭据，When assistant 调用 `bamboohr_list_time_off_requests` 并传入某单个自然日的 `start`/`end`，Then 返回结构化 JSON 数组，其中每条记录至少包含员工姓名、员工 ID、假别、起始日期、结束日期、状态、时长/数量（若上游提供）。
- **AC2**：Given 同上凭据，When 传入覆盖一整周的 `start`/`end` 日期范围，Then 返回该周范围内全部匹配记录，不局限于单日。
- **AC3**：Given 传入 `status=approved` 过滤，When 调用该工具，Then 返回结果只包含状态为 approved 的记录。
- **AC4**：Given 传入 `employeeId` 过滤，When 调用该工具，Then 只返回该员工的记录。
- **AC5**：Given 未配置任何 BambooHR 凭据（gateway 模式缺 `domain`/`api-key` header，或 env 模式缺环境变量），When 调用该工具，Then 返回明确的「缺凭据」错误文案，不抛出未处理异常。
- **AC6**：Given BambooHR 上游返回错误状态码（如 400/401/403），When 调用该工具，Then 工具把上游错误状态码与说明原样转发给调用方，不静默吞掉。
- **AC7**：Given 查询范围内没有任何请假记录，When 调用该工具，Then 返回空数组而非报错。
- **AC8**：Given 两个不同租户（不同 domain/api-key）并发调用该工具，When 请求同时进行，Then 各自只返回各自租户的数据，互不串号（多租户隔离）。

### Open Questions

- **[已假设]** 工单原始 Open Question「默认只返回 approved 还是要求显式 `status=approved`」——本设计假设：工具不设默认值，原样透传 BambooHR 的 `status` 过滤语义（不传即不过滤，返回全部状态），由 SOP 侧的 prompt 按需显式传 `status=approved`。若不成立，需重做「方案 4.3」与技术设计「改动清单」。
- **[不阻塞]** 「响应字段是否要标准化 `amount`/`duration` 格式」——MVP 按原样透传上游 JSON，不做归一化；后续如证明 SOP 生成质量因此受损，可再加映射层（见技术设计 §10 后续迭代）。
- **[不阻塞]** 「`type` 过滤需要 BambooHR 数字类型 ID 而非可读名称」——本单不提供名称→ID 查询工具，SOP 若要用该过滤需自行知道租户的 time-off type id；已记入非目标。
- **[已假设]** 「哪个 BambooHR 账户」——沿用现有 gateway 凭据模型（domain+api-key 按请求传入），与其它四个工具完全一致，不需要额外的租户/凭据判定逻辑。若这一点不成立（例如需要跨账户聚合），需重做技术设计「非功能 · 多租户隔离」一节。
- **[已假设]** 技术设计里假设的响应字段（`employeeId`/`name`/`type.name`/`start`/`end`/`status.status`/`amount`）来自 BambooHR 公开 API 文档，本轮设计没有真实租户凭据可用于实地核验。已在测试用例 TC-BTO-020 里安排一条手工用例，要求在自测阶段用真实/沙盒账号核验一次；若字段名对不上，需回技术设计「数据与接口契约」重做。

## 技术设计

### 结论

在 `bamboohr-mcp` 仓库新增一个只读工具 `bamboohr_list_time_off_requests`，透传调用 BambooHR 现有 `GET /v1/time_off/requests` 接口。复用仓库已有的 `BambooHRClient`/凭据隔离/错误处理机制，不新增依赖、不改上游网关。这是这个仓库里最省的做法：现有四个工具已经把「读 BambooHR 只读接口」这条路径走通了三遍（get/list/list_fields），新工具只是同一形状的第五次复用。

### 现有实现定位

- `src/bamboohr_mcp/tools/employees.py:132-146` `bamboohr_list_employees`——同类「无参数只读列表」工具的现成范本，`register()` 内用 `@mcp.tool()` 装饰、`client_factory()` 取客户端、`client.get(path)` 请求、`_dump()` 序列化、`BambooHRError` 捕获转发。
- `src/bamboohr_mcp/tools/employees.py:107-130` `bamboohr_get_employee`——「带查询参数的只读工具」范本，展示了可选参数如何透传进 `params=` 并允许 `None`。
- `src/bamboohr_mcp/api_client.py:45-54` `BambooHRClient.get()`——通用 GET 封装，`_clean_params` 已经把 `None` 值从 query 里剔除（`api_client.py:40-43`），新工具的可选过滤参数直接受益。
- `src/bamboohr_mcp/server.py:144-147`——工具注册的唯一入口，新增模块只需在这里加一行 `time_off.register(mcp, client_factory)`。
- `tests/test_tools.py:1-104`——现有 respx mock 测试范本，`_client()`/`_basic()`/`_text()` 三个辅助函数可直接复用。

### 数据与接口契约

**MCP 工具签名**（供 assistant/SOP 调用）：

```
bamboohr_list_time_off_requests(
    start: str,                       # 必填，YYYY-MM-DD
    end: str,                         # 必填，YYYY-MM-DD
    status: str | None = None,        # 可选：approved / requested / denied / canceled / superseded
    employee_id: str | None = None,   # 可选，映射为上游 employeeId
    time_off_type_id: str | None = None,  # 可选，映射为上游 type（数字类型 ID，非名称）
) -> str  # JSON 数组文本，_dump() 序列化
```

**上游 API**（BambooHR 网关，透传）：

```
GET {BAMBOOHR_API_ROOT}/{domain}/v1/time_off/requests
Query: start, end, employeeId, status, type
Auth: HTTP Basic（username=api-key, password=BAMBOOHR_BASIC_PASSWORD，与现有 4 个工具一致）
```

响应示例（**字段名来自 BambooHR 公开 API 文档，未对本组织真实租户核验**——见 Open Questions 与 TC-BTO-020）：

```json
[
  {
    "id": "1204",
    "employeeId": "37",
    "name": "Ada Lovelace",
    "status": { "status": "approved", "lastChanged": "2026-08-20", "lastChangedByUserId": "9" },
    "start": "2026-09-08",
    "end": "2026-09-08",
    "created": "2026-08-20",
    "type": { "id": "1", "name": "Vacation" },
    "amount": { "unit": "days", "amount": "1" },
    "dates": { "2026-09-08": "8" }
  }
]
```

- **错误码**：4xx/5xx 全部走现有 `BambooHRError`（`api_client.py:73-83`）——工具返回 `"Error: BambooHR API error <code>: <detail>"`，`<detail>` 优先取上游 `X-BambooHR-Error-Message` header。
- **DB 变更**：无，本工具不落库、不新增表。
- **事件/消息**：无。
- **向后兼容**：纯新增工具，不影响 `bamboohr_create_employee`/`bamboohr_get_employee`/`bamboohr_list_employees`/`bamboohr_list_fields` 现有调用方；MCP `tools/list` 返回的工具清单会多一条，调用方按工具名调用，不存在老客户端因此报错的场景。

### 关键流程时序

```
SOP/assistant → mcp-service-gateway(/mcp) → bamboohr-mcp(/mcp, tools/call)
  1. assistant 决定要生成 Leave Status，调用 bamboohr_list_time_off_requests(start, end[, status][, employee_id])
  2. mcp-service-gateway 按 vendor/registry.yaml 的 bamboohr 条目透传请求（不解析工具名）
  3. bamboohr-mcp 的 GatewayCredsMiddleware 校验 domain/api-key header 存在（缺失 → 401，工具代码不执行）
  4. time_off.register 里的工具函数取 client_factory() → BambooHRClient.get("/time_off/requests", params)
  5. BambooHRClient 发起 HTTP Basic Auth 请求到 BambooHR 网关
  6a. 成功 → _dump(result) 原样返回 JSON 数组文本
  6b. 上游 4xx/5xx → BambooHRError → 工具返回 "Error: ..." 文本
```

### 非功能

- **幂等与并发**：只读 GET，天然幂等，重复调用不产生副作用；并发请求之间通过 `contextvars`（`server.py:18-23`）隔离凭据，与现有四个工具共用同一套机制，不需要新增锁或去重逻辑。
- **性能**：BambooHR 该接口按公开文档不支持分页，单次请求返回 `start`~`end` 区间内全部匹配记录；对超大公司+超长日期范围的响应体积没有客户端限流。工单场景是「日/周级 SOP 定时触发」而非用户实时交互路径，判断当前不需要专门的性能优化；工单与产品设计均未给出明确 SLA，记为已知缺口（TC-BTO-014，`[需求缺失/INCOMPLETE]`），建议 SOP 侧把查询粒度控制在天/周级别而不是月/年级别。
- **安全**：鉴权点与现有四个工具完全一致（Basic Auth + per-request header 隔离）；越权面没有新增（不写入、不暴露新的凭据存储路径）；日志方面这个仓库目前没有结构化日志基础设施（`server.py`/`api_client.py` 均只有一处 `print` 到 stderr 的警告），本工具不额外新增日志，维持仓库现状，不在本单范围内补日志基础设施。
- **多租户隔离**：租户维度完全落在 `domain`/`api-key` 两个请求头上，`contextvars` 保证并发请求不串号（AC8/TC-BTO-011）；没有跨租户共享缓存或全局状态。
- **可观测**：无新增指标/日志，与仓库现状一致；出问题时的定位手段与现有四个工具相同——`BambooHRError` 里带上游状态码与 `X-BambooHR-Error-Message`。

### 上线与回滚

- 无 feature flag 机制（这个仓库本身没有 flag 框架），新工具随镜像发布即生效——MCP 工具是「注册即可调用」，assistant/SOP prompt 侧需要额外知道这个工具名才会使用它，等同于软性灰度。
- 发布顺序：单仓库改动（`bamboohr-mcp`），不依赖 `mcp-service-gateway` 或 `mspbots-agent-mcp` 同步发布（已用代码核实两者是纯透传，见「现状」）。
- 回滚：revert 本单的提交、重新构建 Docker 镜像并重新部署即可；无 DB 迁移、无数据变更，回滚零残留。
